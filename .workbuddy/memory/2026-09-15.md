# 2026-09-15

## 项目认知 / 需求背景

- 用户在评估 LiteLLM 作为**公司内部 LLM 网关**的可行性，核心诉求是「给员工分配虚拟 key，按用量计量」。
- 已确认代码事实（v1.102.0）：
  - 虚拟 key 走 `/key/generate`（`litellm/proxy/management_endpoints/key_management_endpoints.py`），请求模型 `GenerateKeyRequest` 在 `litellm/types/proxy/management_endpoints/key_management_endpoints.py`。
  - 可限维度：`max_budget` + `budget_duration`、`tpm_limit`/`rpm_limit`、`max_parallel_requests`、`models` 白名单、`model_max_budget`、`expires`、`max_budget` 支持 soft_budget。
  - 预算拦截：`proxy/hooks/max_budget_limiter.py`，配合 `proxy/spend_tracking/budget_reservation.py` 做原子预扣，不是纯事后统计。
  - 计量出口：`/spend/logs`、`/global/spend/report`、`/key/spend/report`、响应头 `x-litellm-response-cost`。
  - 花费写入是异步批量（Redis 队列 + `update_spend` 每 60s 落 Postgres），给用户的报表有分钟级延迟。
  - `apply_enterprise_key_management_params` 来自 `litellm_enterprise`，部分 key 管理参数属于企业版。
- 与用户的沟通偏好：中文，直接给结论 + 可复制的命令，少铺垫。

## 交付物

- 写了 `private-llm-deployment-plan.md`（项目根目录）：单机私有化大模型完整实施方案，含 6 个阶段（OS/驱动CUDA/选型/vLLM/LiteLLM 网关/验证排障）+ 版本兼容 + 端口 + 备份升级。架构是「vLLM(8000) + LiteLLM 网关(4000) + Postgres + Redis」。
- 关键版本事实（2026-09 核实）：
  - vLLM stable 0.29.0；CUDA 13.x 需 R580+ 驱动（13.0→R580, 13.2→R595, 13.3→R610, 13.4→R615）；R580 是 LTS 分支（支持到 2028 年中），R535 已 EOL，R610 是 New Feature 分支不适合生产。
  - CUDA 13.0 起移除 CC<7.5（pre-Turing）离线编译支持，V100 及更老卡须留在 CUDA 12.9 + R580。
  - vLLM 默认 wheel 为 CUDA 12.9/13.0；docker 镜像 `vllm/vllm-openai:<固定tag>`。
  - 2026 年中文开源模型首选 Qwen3 系列（Apache 2.0），推理型 DeepSeek-R1-Distill-Qwen-32B，代码 Devstral Small 2 24B；MoE 旗舰（GLM-5、DeepSeek-V4、Qwen3-235B）需多卡。
- 用户的硬件信息尚未提供（GPU 型号/显存/卡数、是否有外网），方案里按档位给了分支并列出 14 项待确认清单。
