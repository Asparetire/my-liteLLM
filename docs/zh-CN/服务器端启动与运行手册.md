## 0. 三个先记住的结论

1. **数据库是硬依赖。** `litellm/proxy/schema.prisma` 写死 `provider = "postgresql"`，仓库没有 SQLite 变体。虚拟密钥、预算、token 配额、用量日志全靠它。没有库时 proxy 能起来，但只能验 UI 和错误文案，计费改造验不了。
2. **单实例不需要 Redis，多实例必须要。** 预算扣减、限流、预留机制跨实例协调依赖 Redis。单实例验证阶段可以先不装。
3. **容器里用 `db:5432`，宿主机上用 `localhost:5432`。** `docker-compose.yml` 里给 `litellm` 服务配的 `@db:5432` 是容器内网互通用的主机名；你的进程跑在宿主机上就得用 `localhost`。这是上路第一个坑。

## 1. 端口总表

| 端口 | 服务 | 暴露建议 | 说明 |
|---|---|---|---|
| **4000** | LiteLLM proxy（后端 + `/ui` 控制台） | 内网 / 经反向代理 | `--port` 默认值即 4000（`litellm/proxy/proxy_cli.py:667`），可用 `PORT` 环境变量覆盖 |
| 3000 | Next.js 开发服务器 | 仅开发机 | 只在 `npm run dev` 双进程模式下使用，生产不启 |
| 5432 | PostgreSQL 16 | 仅内网 | 生产不建议映射到宿主机 |
| 6379 | Redis | 仅内网 | 多实例部署时必需 |
| 9090 | Prometheus | 仅内网 | 仓库根已有 `prometheus.yml`，默认抓 `litellm:4000` |
| 3128 | Squid（`docker-compose.hardened.yml`） | 仅内网 | 加固编排里强制出网走代理 |

改端口两种方式：

```bash
# 命令行
python litellm/proxy/proxy_cli.py --config /app/config.yaml --host 0.0.0.0 --port 4000

# 或环境变量（proxy_cli.py 的 --host/--port 都声明了 envvar）
export HOST=0.0.0.0
export PORT=4000
```

`--host` 默认值就是 `0.0.0.0`（`proxy_cli.py:666`），容器内不用特意改。

## 2. 环境准备

### 2.1 基础软件

```bash
# 系统包
sudo apt update && sudo apt install -y git curl ca-certificates build-essential

# Docker（官方源，含 compose 插件）
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg \
  | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" \
  | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null
sudo apt update && sudo apt install -y docker-ce docker-ce-cli containerd.io \
  docker-buildx-plugin docker-compose-plugin

sudo usermod -aG docker "$USER"   # 重新登录后生效
docker compose version            # 验证
```

### 2.2 裸机路线才需要：Python + uv

只跑 Docker 的话跳过本节。

```bash
# Python 3.11 ~ 3.14 均可（项目要求 >=3.10,<3.15，推荐 3.12）
sudo apt install -y python3.12 python3.12-venv

# uv（用 pip 装，避免 curl | bash 这类管道执行远程脚本）
python3.12 -m pip install --user uv
```

国内机器务必配镜像，否则 `files.pythonhosted.org` 会超时：

```bash
export UV_DEFAULT_INDEX="https://pypi.tuna.tsinghua.edu.cn/simple"
export UV_HTTP_TIMEOUT=120
export PIP_INDEX_URL="https://pypi.tuna.tsinghua.edu.cn/simple"
```

## 4. 依赖安装

### 4.1 Docker 路线（推荐，服务器首选）

不需要在宿主机装 Python 依赖，全部在镜像里：

```bash
cd litellm-cn
docker compose build litellm        # 基于仓库根 Dockerfile，target: runtime
```

首次构建会拉基础镜像并装全套 Python 依赖，耗时较长，放后台跑即可。

### 4.2 裸机路线

```bash
cd litellm-cn

# 装 proxy 全套依赖（与仓库 Makefile 的 install-proxy-dev 一致）
uv sync --frozen --group proxy-dev --extra proxy

# 生成 Prisma Client（不生成的话 proxy 启动会报 prisma 相关 ImportError）
uv run python scripts/prisma_generate_if_needed.py
```

说明：

- `--frozen` 严格按 `uv.lock` 装，保证与 CI 版本一致；`--inexact`（`make install-dev` 的用法）是不剪掉已装的 extras
- `make bootstrap` 等价于上面两步 + UI 依赖安装，但脚本里有 nvm / git worktree 等依赖，服务器上建议按上面手工执行

### 4.3 UI 依赖（只在需要重新构建前端时才装）

```bash
cd ui/litellm-dashboard
npm ci
```

Node 要求 `>=24.14.1`（`package.json` engines）。仓库已提交预构建产物 `litellm/proxy/_experimental/out/index.html`，所以**不改前端就不用装 node_modules**。

## 5. 配置文件调整

### 5.1 `.env`

仓库根只有 `.env.example`，**没有 `.env`**（而 `docker-compose.yml` 里 `litellm` 服务写了 `env_file: - .env`，缺文件会报错）。先复制再改：

```bash
cp .env.example .env
```

参考 `.env.example` 的写法，生产至少要改这三项：

```bash
# 管理密钥：绝不能用默认的 sk-1234
LITELLM_MASTER_KEY="sk-<随机长串>"
# 数据库：容器互通用 db，宿主机进程用 localhost
DATABASE_URL="postgresql://llmproxy:dbpassword9090@db:5432/litellm"
# 允许通过 UI 加模型
STORE_MODEL_IN_DB="True"
```

生成随机 master key：

```bash
python3 -c "import secrets; print('sk-' + secrets.token_urlsafe(32))"
```

### 5.2 `config.yaml`

不要用 `litellm/proxy/dev_config.yaml`（它指向 OpenAI / Anthropic / Bedrock / Vertex，全都要云 API Key）。新建自己的配置，示例：

```yaml
model_list:
  # 本地 Ollama 示例
  - model_name: qwen3.5
    litellm_params:
      model: ollama_chat/qwen3.5:9b
      api_base: http://127.0.0.1:11434
      # 关键：计费改造阶段 A —— 令 spend 数值等于 token 数
      input_cost_per_token: 1.0
      output_cost_per_token: 1.0

  # 国内云模型示例（密钥走环境变量，禁止明文入库）
  - model_name: qwen-plus
    litellm_params:
      model: openai/qwen-plus
      api_base: https://dashscope.aliyuncs.com/compatible-mode/v1
      api_key: os.environ/DASHSCOPE_API_KEY

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY   # 不落明文
  database_url: os.environ/DATABASE_URL
  # 允许 Prometheus 抓取详细 readiness（生产默认关闭，保持注释即可）
  # allow_public_health_readiness_details: true

litellm_settings:
  drop_params: true
  request_timeout: 600
```

要点：

- **所有密钥用 `os.environ/XXX` 引用**，这是 `dev-plans/09` 的硬性验收项
- `input_cost_per_token: 1.0` 是计费改造（需求 05）的第一阶段，零改码就能让 `spend` 等于 token 数、让 `max_budget` 真正生效。若沿用 `0`，`spend` 恒为 0，配额形同虚设
- 多实例时在 `litellm_settings` 加 Redis 配置，变量名为 `REDIS_HOST` / `REDIS_PORT`（仓库示例配置 `litellm/proxy/example_config_yaml/multi_instance_simple_config.yaml` 用的就是这两个）

### 5.3 Prometheus（可选）

仓库根的 `prometheus.yml` 已配好抓 `litellm:4000`。宿主机部署时把 target 改成实际地址：

```yaml
scrape_configs:
  - job_name: 'litellm'
    static_configs:
      - targets: ['<服务器内网IP>:4000']
```

## 6. 启动命令

### 方式 A：Docker 全栈（推荐）

```bash
cd litellm-cn

# 只想让宿主机跑 proxy、容器只提供数据库时：
docker compose up db -d

# 全栈（proxy + Postgres + Prometheus）：
docker compose up -d
```

注意：`docker compose up -d` 会起 `litellm` 服务，用的是**镜像里的代码**（`image: docker.litellm.ai/berriai/litellm:main-stable`）。要跑自己改过的代码，先 `docker compose build litellm`，或改走方式 B。

数据库起来后确认：

```bash
docker compose ps                 # db 应为 healthy
docker compose logs -f db
```

### 方式 B：宿主机直跑 proxy（改代码即见效，推荐开发/联调用）

```bash
cd litellm-cn
export DATABASE_URL="postgresql://llmproxy:dbpassword9090@localhost:5432/litellm"
export LITELLM_MASTER_KEY="sk-xxx"

# 开发模式：热更新 + 详细日志
uv run python litellm/proxy/proxy_cli.py \
  --config ./config.yaml \
  --host 0.0.0.0 --port 4000 \
  --detailed_debug --reload

# 生产模式：多 worker
uv run python litellm/proxy/proxy_cli.py \
  --config /etc/litellm/config.yaml \
  --host 0.0.0.0 --port 4000 \
  --num_workers 4
```

两个约束（`proxy_cli.py:938`）：`--reload` 与 `--num_workers>1`、`--run_gunicorn`、`--run_hypercorn` 互斥；多 worker 需 `uvicorn>=0.37.0`。

**不用手工建表**：proxy 启动时会执行 `prisma migrate deploy` 自动建全部表，前提是 `DATABASE_URL` 在启动前已设置。

### 方式 C：systemd 托管（长期运行）

```ini
# /etc/systemd/system/litellm.service
[Unit]
Description=LiteLLM Proxy
After=network.target docker.service
Requires=docker.service

[Service]
Type=simple
User=litellm
WorkingDirectory=/opt/litellm-cn
Environment="DATABASE_URL=postgresql://llmproxy:dbpassword9090@localhost:5432/litellm"
Environment="LITELLM_MASTER_KEY=sk-xxx"
ExecStart=/opt/litellm-cn/.venv/bin/python litellm/proxy/proxy_cli.py \
          --config /etc/litellm/config.yaml --host 0.0.0.0 --port 4000 --num_workers 4
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now litellm
systemctl status litellm
```

若是 Docker 路线，把 `ExecStart` 换成 `docker compose up`、加 `ExecStop=docker compose down` 即可。

### 前端单独起（仅开发）

```bash
cd ui/litellm-dashboard
# 后端不在同源时，必须指定后端地址
echo 'NEXT_PUBLIC_BASE_URL=http://localhost:4000' > .env.local
npm run dev          # 端口 3000
```

跨域不用额外配：proxy 的 CORS 默认 `allow_origins=["*"]`（未设 `LITELLM_CORS_ORIGINS` 时）。

## 7. 启动后如何验证

### 7.1 健康检查端点

| 端点 | 鉴权 | 用途 | 正常表现 |
|---|---|---|---|
| `/health/liveliness` | 无 | 存活探针（K8s liveness） | 200，进程活着 |
| `/health/readiness` | 无 | 就绪探针（K8s readiness） | 200 `{"status":"healthy","db":"connected"}`；**DB 断连时返回 503** |
| `/health/readiness/details` | 需 key | 详细诊断（DB/缓存/回调） | 200，含各依赖状态 |
| `/health/services?service=datadog` | 管理员 | 外部回调连通性测试 | `{"status":"healthy"\|"unhealthy"}` |
| `/health/history`、`/health/latest` | 需 key | 模型健康检查结果历史/最新 | 200 |
| `/health/backlog` | 需 key | 当前 worker 在途请求数 | `in_flight_requests` 等 |
| `/health/drain` | 可选 token | 优雅下线（preStop） | 默认 **404**，需在 `general_settings.enable_drain_endpoint: true` |
| `/metrics` | 无 | Prometheus 指标 | 由 PrometheusLogger 挂载（`litellm/integrations/prometheus.py:4406`） |

```bash
curl -s http://localhost:4000/health/liveliness
curl -s http://localhost:4000/health/readiness; echo
```

### 7.2 接口冒烟测试

```bash
export LITELLM_URL=http://localhost:4000
export KEY=sk-<master key>

# 1. 模型列表
curl -s $LITELLM_URL/v1/models -H "Authorization: Bearer $KEY" | head -c 500; echo

# 2. 真实调用一次
curl -s $LITELLM_URL/v1/chat/completions \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"model":"qwen3.5","messages":[{"role":"user","content":"你好"}],"max_tokens":64}'

# 3. 查用量与花费（计费改造的验收点：spend 应等于 token 数）
curl -s "$LITELLM_URL/key/info" -H "Authorization: Bearer $KEY" | grep -E '"spend"|"max_budget"'

# 4. 建虚拟密钥
curl -s -X POST $LITELLM_URL/key/generate \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"max_budget": 500}'
```

### 7.3 零成本全链路验证（无需任何模型与 API Key）

不想接真实模型时用 `mock_response`：它不调用任何提供商，但返回带 usage 的完整响应，计费与配额逻辑照常执行。

```bash
# 先建一个允许客户端 mock 的密钥（默认会被网关剥离，必须显式开）
curl -s -X POST $LITELLM_URL/key/generate \
  -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" \
  -d '{"metadata": {"allow_client_mock_response": true}, "max_budget": 500}'

# 用返回的 key 反复调用，直到 500 用尽
curl -s $LITELLM_URL/v1/chat/completions \
  -H "Authorization: Bearer <上一步的 key>" -H "Content-Type: application/json" \
  -d '{"model":"mock-model","messages":[{"role":"user","content":"hi"}],"mock_response":"hello"}'
```

预期：前若干次正常返回且带 usage，配额耗尽后返回 **429**。这条路径是计费/配额改造的标准冒烟动作。

### 7.4 状态页面

- 控制台：`http://<服务器IP>:4000/ui/`（proxy 把构建产物挂在 `/ui`，见 `proxy_server.py:2135`），用 master key 登录
- Prometheus：`http://<服务器IP>:9090`
- Swagger 文档：`http://<服务器IP>:4000/docs`

> 注意：仓库里 `litellm/proxy/_experimental/out/` 提交的是**上游预构建产物**，不含你的前端改动。要看自己的汉化效果，得重新 `npm run build` 后把 `ui/litellm-dashboard/out/` 覆盖过去，或者用 3000 端口的开发服务器。

### 7.5 日志

```bash
# Docker
docker compose logs -f litellm
docker compose logs -f --tail 200 litellm

# systemd
journalctl -u litellm -f
journalctl -u litellm --since "10 min ago" -p warning

# 前台直跑时，加 --detailed_debug 打开详细调试日志
```

关键启动日志节点：Prisma 迁移完成、`Uvicorn running on http://0.0.0.0:4000`、模型加载完成。看到这三行基本就起来了。

## 8. 如何跟踪开发进度

| 想看什么 | 怎么看 |
|---|---|
| 需求拆解与优先级 | `dev-plans/README.md` 与 01~13 号文档，每份开头有「状态」一栏 |

| 运行时是否健康 | 第 7 节的健康检查 + `/metrics` |

## 9. 常见故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报缺 `os.environ/OPENAI_API_KEY` | 用了 `litellm/proxy/dev_config.yaml` | 换自己的 `config.yaml` |
| 密钥/预算接口报错，UI 部分页面空白 | 没连上数据库 | 确认 Postgres 已起、`DATABASE_URL` 已设置；宿主机用 `localhost` 而非 `db` |
| `prisma` 相关 ImportError | 没生成 Prisma Client | 执行 `uv run python scripts/prisma_generate_if_needed.py` |
| `/health/readiness` 返回 503 | 数据库不可达 | 查 db 容器状态与连接串 |
| 4000/ui 看不到自己的汉化 | 那是仓库预构建产物 | 重新 build 前端并覆盖，或用 3000 端口开发服务器 |
| `spend` 一直是 0 | `input_cost_per_token` 写成了 0 | 改成 `1.0`（计费改造阶段 A） |
| uv 卡在下载依赖 | PyPI 官方 CDN 超时 | 配 `UV_DEFAULT_INDEX` 国内镜像 |
| 多实例下预算不准 | 缺共享 Redis | 补 Redis 并在配置里填 `REDIS_HOST` / `REDIS_PORT` |
| `make bootstrap` 失败 | 脚本依赖 nvm / git worktree 等 | 按第 4 节手工执行 |

## 10. 验收清单

- [ ] `docker compose ps` 或 `systemctl status litellm` 显示运行中
- [ ] `curl /health/liveliness` 返回 200
- [ ] `curl /health/readiness` 返回 `{"status":"healthy","db":"connected"}`
- [ ] Postgres 可连接，虚拟密钥能创建并持久化
- [ ] `/v1/models` 能列出配置的模型
- [ ] 一次真实（或 mock）调用返回带 usage
- [ ] `/key/info` 里 `spend` 有值，且与 token 数一致（计费改造验证点）
- [ ] 配额耗尽返回 429
- [ ] 浏览器打开 `:4000/ui/`（或 `:3000`）能用 master key 登录
- [ ] master key 已替换默认值，配置里无明文密钥
- [ ] `/metrics` 能被 Prometheus 抓到（如启用）
