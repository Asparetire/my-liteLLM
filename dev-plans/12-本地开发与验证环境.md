### 2.1 为什么不用 Anaconda（实测结论）

本机确实装了 Anaconda，但**不能用于这个项目**，三条硬理由：

1. **版本过低，直接不达标**：`C:\ProgramData\anaconda3\python.exe` 实测为 **Python 3.7.0（2018-06-28 构建，Anaconda3 5.3.1 64-bit）**，而 `pyproject.toml` 要求 `requires-python = ">=3.10, <3.15"` —— 连下限都没到。这台机器上 Anaconda 只有一个 base 环境，没有其他 env。
2. **不在 PATH，且会污染工具链**：实测用户与系统 PATH 里**没有任何 conda 条目**，`conda activate` 直接不可用。而把 Anaconda 的 `Scripts` / `Library\bin` 加进 PATH 是"搞坏其它命令行工具"的经典原因——它自带一套 `libssl` / `libcrypto` / `zlib` DLL，会与 Git Bash、curl 等抢加载顺序。
3. **与项目的依赖锁机制冲突**：项目用 `uv` + `uv.lock`（镜像里跑的是 `uv sync --frozen`）保证依赖可复现。往 conda base 里 `pip install` 业务依赖，既破坏锁文件一致性，也违反 conda 自身规范（base 环境不应装项目依赖）。

**结论：conda base 不能用，但"新建一个 conda 环境"完全可行——本项目就是这么做的**（见 2.3，已建好 `litellm-cn` 环境，Python 3.13.15）。需要注意的只是：**别把 conda 的安装目录加进全局 PATH、别往 base 里装业务依赖**。日常开发激活 `litellm-cn` 环境即可，与 uv 并不冲突：conda 负责提供 Python 解释器，uv 负责按 `uv.lock` 装依赖。

> 补充：若你新装的 Anaconda 不在 `C:\ProgramData\anaconda3`（即上表这只是台机器上的历史遗留），把这个路径告诉我，我再核一遍版本。

### 2.2 如果确实要配置 Anaconda 的环境变量

先说一个实测出来的**决定性限制**：

```
& C:\ProgramData\anaconda3\Scripts\conda.exe init --help
→ CommandNotFoundError: No command 'conda init'.
```

`conda init` 是 **conda 4.6.0 才引入**的，而这台机器上是 **conda 4.5.11**。这意味着**现代那套"一条命令配好、不用手碰 PATH"的标准做法在这里不可用**，只能退回手工配置或手动激活。

同样在 4.6.0 才引入、因此在 4.5.11 上**也撞墙**的还有 `conda run`：

```
& C:\ProgramData\anaconda3\Scripts\conda.exe run -n base python --version
→ CommandNotFoundError: No command 'conda run'.
```

即 **`conda init` 和 `conda run` 这两个教程里最常用的命令在这里都没有**，替代方案见方式一。

另一个实测结论（好消息）：4.5.11 的源连接与索引解析**仍然正常**，能列到 `python 3.13.15`（`pkgs/main`），所以 `conda create -n xxx python=3.13` 理论可行——但不建议这样做。

#### 配置方式一：不动环境变量（最安全，推荐）

直接用绝对路径调用，零配置、零污染：

```powershell
# conda.exe 本体在 Scripts 目录，实测可直接调用
$conda = "C:\ProgramData\anaconda3\Scripts\conda.exe"

& $conda --version
& $conda create -n py313 python=3.13

# 注意：没有 `conda run`（4.6.0 才引入）
# 想在某个环境里跑东西，直接用该环境的 python.exe 绝对路径 —— 零配置、最可靠
& "C:\ProgramData\anaconda3\envs\py313\python.exe" --version
```

cmd 下激活环境（实测两个位置都有可用入口）：

```cmd
REM 方式 a：Scripts 里的 activate.bat
call C:\ProgramData\anaconda3\Scripts\activate.bat py313

REM 方式 b：Library\bin 里的 conda.bat —— Windows 上 conda 的规范包装器
call C:\ProgramData\anaconda3\Library\bin\conda.bat activate py313
```

> **更正一个我此前说错的点**：`conda.bat` **存在**，只是不在 `Scripts` 而在 `Library\bin`（2146 字节，实测 `conda.bat --version` 正常返回 `conda 4.5.11`）。这才是 Windows 上 `conda.bat` 的规范位置；我一开始只查了 `Scripts` 目录就下了"文件缺失"的结论，是错的。
>
> `conda.bat` 的价值在于让 `conda activate` 这种"需要修改当前 shell"的子命令可用：它把 `activate` 转发给 `conda.exe shell.cmd.exe activate`，拿到一个临时脚本再 `CALL` 执行（源码第 30-38 行）。所以**cmd 里想用 `conda activate <env>` 这种写法，需要 `Library\bin` 在 PATH 里**；只放 `Scripts` 时命令名是 `activate <env>`。
>
> `Scripts` 里另有一对 `activate` / `deactivate`（**无扩展名**，137 / 134 字节）——那是给 **Git Bash 用的 shell 脚本**，bash 里 `source` 它们即可。

> PowerShell 里**无法**用这些 .bat 激活当前会话（`.bat` 不能修改父 shell 的环境变量），得 `cmd /k "..."` 另开窗口，或直接用环境内 python.exe 的绝对路径。这同样是老版本 conda 缺 PowerShell 集成的表现。

#### 配置方式二：把 conda 加进用户级 PATH

**只动用户级（`HKCU`），不要动系统级（`HKLM`）**，避免影响其他账户、也不需要管理员。

先看清每个目录放进去分别换来什么（DLL 数量为实测值）：

| 目录 | 提供什么 | DLL 数量 | 评价 |
|---|---|---|---|
| `Scripts` | `conda`（conda.exe）、`activate`、`deactivate`（.bat 与 bash 两套） | **0** | ✅ **首选**，最干净 |
| `Library\bin` | `conda.bat`（让 `conda activate` 可用）、一批 C 库 | **212** | ⚠️ 仅当需要 `conda activate` 写法时才加 |
| `Library\mingw-w64\bin` | MinGW 工具链 | — | 一般不需要 |
| `Library\usr\bin` | MSYS 工具链 | — | 一般不需要 |
| `anaconda3`（根目录） | 让裸 `python` 指向 conda base | 5（在 `DLLs\`） | ❌ **建议不加**，与项目要求冲突 |

**最保守配置（一个目录覆盖绝大部分场景）：**

```powershell
$cur = [Environment]::GetEnvironmentVariable('PATH','User')
[Environment]::SetEnvironmentVariable('PATH', "$cur;C:\ProgramData\anaconda3\Scripts", 'User')
```

**完整配置（官方安装器的默认行为，需要 `conda activate` 就用这个）：**

```powershell
$cur = [Environment]::GetEnvironmentVariable('PATH','User')
$add = @(
  'C:\ProgramData\anaconda3\Scripts',
  'C:\ProgramData\anaconda3\Library\mingw-w64\bin',
  'C:\ProgramData\anaconda3\Library\usr\bin',
  'C:\ProgramData\anaconda3\Library\bin'
) -join ';'
[Environment]::SetEnvironmentVariable('PATH', "$cur;$add", 'User')
```

> ⚠️ **三条共同注意事项**
> 1. **必须追加到末尾，绝不能放前面。** 放前面会让裸 `python` 解析到 **3.7.0**，而项目要求 `>=3.10`。
> 2. **不要加 `C:\ProgramData\anaconda3` 根目录**，除非你确实想让裸 `python` 变成 conda base 的 3.7.0。
> 3. 改完必须**重开终端**才生效（已运行的进程读的是旧环境块）。

#### 可选环境变量

| 变量 | 建议 | 说明 |
|---|---|---|
| `CONDA_EXE` | 可设 | `C:\ProgramData\anaconda3\Scripts\conda.exe`。注意本机 4.5.11 的 `conda.bat` 用的是自己算出来的内部变量 **`_CONDA_EXE`**（源码第 1-5 行），所以手工设它对本机激活流程基本没有影响 |
| `CONDA_PYTHON_EXE` | 可设 | `C:\ProgramData\anaconda3\python.exe`，同上，一般由脚本维护 |
| `CONDA_SHLVL` | ❌ 别手工设 | 记录"已激活"层数，由 activate 脚本维护。手工设会造成状态不一致 |
| `PYTHONIOENCODING` | ⚠️ **别设** | 见下方说明，本机的 conda.bat 把它劫持成代码页参数了 |
| `PYTHONUTF8` | `1` | 想要 UTF-8 就用这个替代 —— Python 3.7+ 的 UTF-8 模式，conda.bat 不读它，无副作用 |
| `CONDA_PKGS_DIRS` | 按需 | 如 `D:\conda-pkgs`。包缓存默认堆在 `anaconda3\pkgs`，很吃 C 盘 |

> ⚠️ **`PYTHONIOENCODING` 在这台机器上有个坑。** `Library\bin\conda.bat` 第 40 行是：
>
> ```bat
> @IF DEFINED PYTHONIOENCODING chcp %PYTHONIOENCODING% > NUL
> ```
>
> 它把这个变量的值**直接当作代码页编号**喂给 `chcp`。也就是说一旦设成 `utf-8`，语义就被劫持了——`chcp utf-8` 并不是合法的代码页参数（合法的是 `chcp 65001`），而 `> NUL` 只吞掉 stdout，报错仍可能冒到 stderr。
>
> **要 UTF-8 输出请改用 `PYTHONUTF8=1`**（Python 3.7+ 的 UTF-8 模式），conda.bat 不读这个变量，没有任何副作用。这也是我此前那条"推荐加 `PYTHONIOENCODING=utf-8`"建议的修正。

- `C:\ProgramData\anaconda3\Library\bin` 实测有 **212 个 DLL**，含 `zlib.dll`、`libcurl.dll`、`libssh2.dll`。加进 PATH（尤其靠前）会污染其它进程的动态库加载顺序，典型症状是 Git / curl 报莫名其妙的错

#### 必须由你在终端执行：同步依赖

**这一步无法在自动化沙箱内完成**，原因已定位清楚：uv 使用 `\\?\` 前缀的 verbatim 路径做原子写入，沙箱的路径过滤拦截了这种形式，一律返回 `os error 5 拒绝访问`。这不是文件权限问题（同一个目录用普通方式写入是通的），而是沙箱行为。

另外还有两个**必须**注意的点：

- **PyPI 官方 CDN（`files.pythonhosted.org`）在国内会超时**。首次尝试即卡死在此（`Failed to download psycopg-binary`，重试 4 次、耗时 123s），必须换国内镜像。
- 缓存已下好 **613.8 MB** 到 `D:\project\litellm-cn\.uv-cache`，**保留它**（已加入 `.gitignore`），复用可省掉重新下载。

在你自己的 PowerShell 窗口里执行：

```powershell
# 1) 临时把 conda 环境放到 PATH 最前（PowerShell 下相当于激活，仅影响当前窗口）
$env:Path = "C:\ProgramData\anaconda3\envs\litellm-cn;C:\ProgramData\anaconda3\envs\litellm-cn\Scripts;" + $env:Path

# 2) 国内镜像（必需）
$env:UV_DEFAULT_INDEX = "https://pypi.tuna.tsinghua.edu.cn/simple"
$env:UV_HTTP_TIMEOUT  = "120"

# 3) 复用已下好的缓存
$env:UV_CACHE_DIR = "D:\project\litellm-cn\.uv-cache"

# 4) 让 uv 把依赖装进 conda 环境，而不是另建 .venv
$env:UV_PROJECT_ENVIRONMENT = "C:\ProgramData\anaconda3\envs\litellm-cn"

# 5) 安装（与项目 Makefile 一致）
cd D:\project\litellm-cn
uv sync --inexact --frozen --extra proxy
```

验证：

```powershell
python -c "import litellm, fastapi, uvicorn; print(litellm.__version__)"
```

## 3. 一次性安装步骤

### 3.1 安装 uv

**本机已完成**（装在 conda 环境 `litellm-cn` 内，见 2.3）。若要在别处重装：

```powershell
# 装进 conda 环境（本机采用的方式）

```

用 pip 装而不是官方安装器，是为了避免 `curl | bash` 这类管道执行远程脚本。装完后 uv 位于 `envs\litellm-cn\Scripts\uv.exe`，激活环境后即可直接用 `uv` 命令。

### 3.2 安装 Python 依赖（proxy 全套）

**⚠️ 本机这一步必须在你自己终端执行，命令与原因见 [2.3](#23-已落地的方案conda-环境--uv-管依赖)。** 核心命令：

```powershell
cd D:\project\litellm-cn
uv sync --inexact --frozen --extra proxy
uv run python scripts/prisma_generate_if_needed.py
```

- `--inexact` 是仓库 Makefile 里的既定用法：不把已装的 extras 剪掉
- `--frozen` 依赖仓库里的 `uv.lock`，保证版本一致
- 首次下载数百 MB（本机实测缓存 613.8 MB，视网络 5-15 分钟）
- **默认会在项目根建 `.venv`**；本机改用 `UV_PROJECT_ENVIRONMENT` 指向 conda 环境，因此**不会**生成 `.venv`
- **必须配国内镜像**，否则会卡在 `files.pythonhosted.org` 超时

> 仓库的 `make bootstrap` 等价于以上全部 + UI 依赖安装，但 **Windows 上 make 不一定可用**，且该脚本里有 nvm/rm/cp 等 Unix 依赖，建议按本文的命令手工执行。

### 3.3 安装 UI 依赖

```powershell
cd D:\project\litellm-cn\ui\litellm-dashboard

```

注意两点：

- **必须先让 node 走 24.x**（见第 6 节），否则 Next 16 起不来
- 仓库有 `package-lock.json`，所以用 `npm ci`（严格按锁文件装）；npm install 也行但会漂版本

| CPU 虚拟化（i7-9700） | ✅ `VirtualizationFirmwareEnabled=True`、SLAT ✅、VT-x ✅ |
| 系统 | Windows 10 专业版 19045（22H2） |
| 内存 / 磁盘 | 31.8 GB / C 剩 182 GB、D 剩 191 GB ✅ |
| 端口 5432 / 4000 / 3000 | 均空闲 ✅ |

即**硬件与系统都满足，但必须先开功能并重启一次**。顺序如下（当前会话实测已是管理员，可直接执行）：

```powershell
# 1. 启用 WSL 与虚拟机平台
dism.exe /online /enable-feature /featurename:Microsoft-Windows-Subsystem-Linux /all /norestart
dism.exe /online /enable-feature /featurename:VirtualMachinePlatform /all /norestart

# 2. 重启电脑 —— 这步无法跳过

# 3. 重启后将 WSL 默认版本设为 2，再装 Docker Desktop
wsl --set-default-version 2
winget install --id Docker.DockerDesktop -e
```

起数据库：

```powershell
cd D:\project\litellm-cn
docker compose up db -d
```

> ⚠️ **只起 `db`，不要 `docker compose up -d`。** 整份 compose 还含 `litellm`（会去 build 镜像，耗时数百 MB 下载+构建）和 `prometheus`，全量启动既慢又没必要。

> ⚠️ **连接串用 `localhost`，不要用 `db`。** compose 里给 litellm 容器配的是 `@db:5432`，那是**容器内互访**的主机名；你的 proxy 跑在宿主机上，必须用 `localhost`。这是 Docker 上路后最容易踩的第一个坑。

> ✅ **不用手工建表。** `proxy_cli.py:1352` 会在启动时调用 `PrismaManager.setup_database(use_migrate=True)`，自动执行 `prisma migrate deploy` 建好全部表——只要启动前 `DATABASE_URL` 已设置即可。相关实现见 `litellm-proxy-extras/litellm_proxy_extras/utils.py`。

> 📌 仓库根**没有 `.env`**（只有 `.env.example`）。compose 中 `litellm` 服务的 `env_file: - .env` 因此指向不存在的文件——只起 `db` 不受影响；将来用方式 C 全栈启动前需先 `copy .env.example .env`。

**方案 B：Windows 原生安装 PostgreSQL 16（零重启备选）**

装完后手工建库建账号，保持一致即可：

```
库名: litellm    用户: llmproxy    密码: dbpassword9090    端口: 5432
```

然后设置环境变量：

```powershell
$env:DATABASE_URL = "postgresql://llmproxy:dbpassword9090@127.0.0.1:5432/litellm"
```

> 为什么必须有数据库：`litellm/proxy/schema.prisma` 第 2 行写死 `provider = "postgresql"`，仓库里没有 SQLite 变体。虚拟密钥、预算、token 配额、用量日志全部依赖数据库。**没有数据库时 proxy 仍能启动**，但只能验证 UI 与错误翻译，计费改造验证不了。

**A 与 B 怎么选**：如果只要一个 Postgres，B 更快（winget 装完即用，不重启）。但 A 的价值在后续——Redis（多实例下限流与预算的强依赖）、把 proxy 本身容器化、以及与公司最终部署环境对齐，都会用到 Docker。既然这是公司级网关选型，建议直接走 A：一次重启，换掉整条后续路径；否则后面为了 Redis 还得再回来补一遍前置条件。

### 3.5 准备你的开发配置

`litellm/proxy/dev_config.yaml` **不能用**：它指向 OpenAI / Anthropic / Bedrock / Vertex，全部需要云 API Key。

新建 `config.dev.cn.yaml`（放仓库根，作为你的自有文件）：

```yaml
model_list:
  # 本地 Ollama（装了 Ollama 才有用）
  - model_name: qwen3.5
    litellm_params:
      model: ollama_chat/qwen3.5:9b
      api_base: http://127.0.0.1:11434
      input_cost_per_token: 1.0     # 关键：见下方说明
      output_cost_per_token: 1.0

  # 占位模型：配合 mock_response 做零成本验证，不需要真实 Key
  - model_name: mock-model
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: sk-dummy-not-used

general_settings:
  master_key: sk-1234
  database_url: os.environ/DATABASE_URL

litellm_settings:
  drop_params: true
  request_timeout: 600
```

**关于 `input_cost_per_token: 1.0`**：你原来的 Ollama 配置里写的是 `0`，这会让 `spend` 恒为 0、`max_budget` 形同虚设。把它改成 `1.0` 正是计费改造需求 05 的第一阶段（零改码），改完 `spend` 的数值就等于 token 数，配额立刻生效——这是你最容易验证的第一个改动。

## 6. 零成本端到端验证：client mock_response

不需要任何模型、任何 API Key，就能跑通「请求 → 计量 → 配额」全链路。

原理：LiteLLM 支持在请求体里传 `mock_response`，它不调用任何提供商，但**会返回带 usage 的完整响应**（prompt / completion / total tokens 都有值，见 `litellm/main.py:989-1000`），因此计费与配额逻辑照常执行。

**关键前提**：客户端传的 `mock_response` 默认被网关剥离，必须在密钥或团队的 metadata 里显式开关（`litellm/proxy/litellm_pre_call_utils.py:316,472`）：

```powershell
# 建一个允许 mock 的密钥
curl -s -X POST http://localhost:4000/key/generate `
  -H "Authorization: Bearer sk-1234" -H "Content-Type: application/json" `
  -d '{"metadata": {"allow_client_mock_response": true}, "max_budget": 500}'
```

拿到返回里的 `key`，然后：

```powershell
curl -s http://localhost:4000/v1/chat/completions `
  -H "Authorization: Bearer <上一步的 key>" -H "Content-Type: application/json" `
  -d '{"model":"mock-model","messages":[{"role":"user","content":"hi"}],"mock_response":"hello"}'
```

- 响应正常返回且带 usage → 说明链路通
- 反复调用直到 `max_budget: 500` 用尽 → 应返回 **429**，说明配额生效
- 把 `input_cost_per_token` 从 1.0 改成 0.5 再测 → 能观察到配额消耗速度变化，说明权重生效

这条路径把计费改造的验证成本降到零，建议作为每次改动后的标准冒烟动作。

## 7. 常见坑（都已踩过或有代码依据）

| 坑 | 现象 | 处理 |
|---|---|---|
| node 版本不对 | `next` 报引擎不满足 / 构建失败 | PATH 里 `22.22.2` 排在前面。先 `$env:PATH = "D:\tool;" + $env:PATH` 再执行 npm 命令；`scripts/with_dashboard_node.sh` 在本机找不到 nvm 会直接退出，别用它 |
| `dev_config.yaml` 缺云 Key | proxy 启动时报缺 `os.environ/OPENAI_API_KEY` | 别用它，用自己的 config（第 3.5 节） |
| 没有数据库 | 密钥/预算接口报错，UI 部分页面空白 | 起 Postgres（第 3.4 节） |
| 全量跑 UI 测试 | 机器卡死几分钟 | 只跑改动涉及的测试文件 |
| `make` 不可用 | `make bootstrap` 失败 | 按本文命令手工执行 |
| 首次安装耗时长 | uv sync / npm ci 跑很久 | 放后台跑，耐心等；不要中断 |
| 预构建 UI 是旧版 | 4000/ui 看不到你的改动 | 那是仓库里提交的产物，需重新 build 覆盖（方式 B） |
| 本机 git 引用异常 | fetch 后分支跟踪显示 `gone` | 见 11 号文档第 6 节的环境怪癖说明 |
