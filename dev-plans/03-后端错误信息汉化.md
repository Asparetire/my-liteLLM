| 项 | 内容 |
|---|---|
| 需求编号 | REQ-03 |
| 优先级 | P1（核心需求一） |
| 预估工作量 | 3-4 天（含 200-300 条高频报错收录） |

| 前置依赖 | 01 仓库基础 |

## 1. 问题定义 ✅

后端提示信息散落在 2000+ 个 Python 文件里（`raise ValueError("...")`、`detail="..."`、校验消息等）。逐个修改的代价与冲突风险都不可接受：

- 改动量巨大，且上游每天都在新增/修改报错文案
- 每次上游同步都会产生大量冲突
- 改错位置可能影响错误码与错误分类逻辑

因此采用**外挂式中拦截翻译**：不动任何上游文件，在 API 响应出口统一翻译。

## 2. 技术方案 ✅

### 2.1 新增独立模块（零上游入侵）✅

```bash
litellm_cn/                          # 新目录，全部为新增文件
├── __init__.py
├── locale/
│   ├── en.json                      # 原文清单（key 与 zh-CN.json 一一对应，便于校验覆盖率）
│   ├── zh-CN.json                   # 原文 -> 译文 映射表
│   └── README.md                    # 使用指南
├── translator.py                    # 纯函数翻译层
├── middleware.py                    # FastAPI 响应中间件 + install(app)
├── test_translator.py               # 单元测试（11 个用例）
└── test_e2e.py                      # 端到端测试（启动 proxy 触发错误响应）
```

### 2.2 模块接口设计 ✅

`translator.py`：

```python
def translate_message(text: str, locale: str = "zh-CN") -> str:
    """命中映射表返回译文，未命中原样返回英文（降级安全）。"""
```

`middleware.py`：

```python
def install(app: "FastAPI") -> None:
    """注册响应中间件：改写 JSON 响应中的 error.message / detail 字段。"""
```

**已实现：** ✅ `translator.py`、`middleware.py`、`locale/zh-CN.json`、`locale/en.json`

**2026-09-17 修复记录（代码审查发现的真实缺陷）：**

1. `middleware.py` 缺少 `Response` 导入，模块导入时即抛 `NameError`；而挂载点只捕获 `ImportError`，会导致代理启动失败。已补齐导入
2. `translator.py` 占位符替换误用 `format(**re.findall(...))`（list 不能用 `**` 展开，抛 `TypeError` 未被捕获）。已改为将模板编译为命名分组正则后全匹配提取参数
3. `"Internal server error"`（空格）无法命中 `error.internal_server_error` key。已加空格归一为下划线的策略
4. 中间件只改写顶层 `message` 字段，未覆盖文档承诺的 `{"detail": ...}` 与 `{"error": {"message": ...}}` 形状；且重建响应时携带旧 `content-length`。已改为递归改写 `error/message/detail` 的字符串值并剔除旧 `content-length`
5. 新增关闭开关：环境变量 `LITELLM_CN_ERROR_TRANSLATION_DISABLED=1/true/yes` 时 `install()` 直接跳过，行为与原生完全一致

### 2.3 挂载点（唯一需要触碰上游文件的位置）✅

已在 `proxy_server.py:1528`（OpenTelemetry 仪器之后、路由注册之前）加带标记的挂载调用：

```python
### [CN-FORK] BEGIN: 中文错误信息中间件 ###
try:
    from litellm_cn.middleware import install as install_cn_middleware

    install_cn_middleware(app)
except ImportError:
    # litellm_cn 模块未安装时跳过（可选功能）
    pass
### [CN-FORK] END ###
```

同时提供开关（默认开启，可通过环境变量关闭）：

```bash
export LITELLM_CN_ERROR_TRANSLATION_DISABLED=1   # 关闭翻译，行为与原生完全一致
```

> 说明：文档早期规划的 `general_settings.cn_locale` config.yaml 形式需要接入 proxy 配置读取链路，暂以环境变量开关替代，config 形式待后续需求接入。

### 2.4 中间件职责 ✅

1. 仅处理 `Content-Type: application/json` 的响应
2. 命中错误结构时才改写：`{"error": {"message": "..."}}`、`{"detail": "..."}`、`{"error": {"message": {"error": "..."}}}` 等 LiteLLM 既有错误形状
3. 只替换**字符串值**，不动字段名与错误类型标识（保证客户端错误处理逻辑不受影响）
4. 异常兜底：翻译过程出错时返回原始响应，绝不因翻译导致接口异常

## 3. 翻译表收录策略 ✅

### 3.1 优先级（按用户可见度）✅

| 优先级 | 类别 | 示例 |
|---|---|---|
| P0 | 认证与权限 | 无效 API Key、Key 已过期、无权访问模型、team/org 配额用尽 |
| P0 | 配额与限流 | Max budget limit reached、TPM/RPM exceeded |
| P1 | 请求参数错误 | 缺少必填字段、模型不存在、参数类型错误 |
| P1 | 上游提供商错误透传 | 提供商 401/429 的标准文案（注意保留原文便于排障） |
| P2 | 内部错误 | 数据库不可用、缓存连接失败等（可后置） |

### 3.2 映射表编写规范 ✅

```json
{
  "Max budget limit reached.": "已达到预算上限。",
  "Authentication Error, Invalid proxy server token passed.": "认证失败：代理服务器令牌无效。"
}
```

- **key 使用英文原文全量字符串**（含标点），避免正则匹配带来的误伤
- 对含变量的文案，使用占位符而非模糊匹配
- 译文中的技术名词保留英文（`API Key`、`TPM`、`model` 等），仅译句子结构

### 3.3 当前翻译覆盖率 ✅

- `zh-CN.json` 收录高频错误 28 条（P0 认证/配额/限流类已覆盖，P1 参数错误类部分覆盖）
- `en.json` 为原文清单，key 与 zh-CN.json 一一对应

## 5. 局限与说明（需向使用者明确）✅

- 仅覆盖**走到 API 响应**的文本；服务端日志仍为英文（排障时英文日志信息量更大，属有意取舍）
- 上游若修改了报错原文，映射表需同步更新；未更新的条目自动回退英文，**不会报错**
- 不翻译上游提供商原样透传的响应体（保留厂商原文便于定位问题）

## 7. 风险与缓解 ✅

| 风险 | 缓解 |
|---|---|
| 上游修改报错文案导致映射表失效 | 未命中条目自动回退英文，降级安全 |
| 翻译错误导致用户体验下降 | 严格测试；保留英文原文便于排障 |
| 正常响应被误改写 | 中间件只处理错误响应结构，有白名单校验 |
