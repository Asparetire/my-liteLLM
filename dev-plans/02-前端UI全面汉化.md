## 2. 技术方案：next-intl

选型理由：对 App Router / RSC 支持最完整，支持「未翻译 key 回退默认语言」，天然满足「降级安全」要求；不引入客户端 bundle 膨胀（服务端渲染翻译）。

### 2.1 目录结构（全部为新增文件）

```
ui/litellm-dashboard/
├── messages/
│   ├── en.json          # 原文（从代码抽取，与上游文案保持一致，作为回退语言）
│   └── zh-CN.json       # 中文译文（唯一需要人力维护的文件）
├── i18n/
│   ├── routing.ts       # locales: ['zh-CN','en']，defaultLocale: 'zh-CN'
│   └── request.ts       # getRequestConfig：按 locale 动态 import messages
├── next.config.ts       # 用 withNextIntl 包裹现有配置（[CN-FORK] 标记）
└── src/middleware.ts    # locale 检测与 cookie 持久化（若已存在 middleware 则合并）
```

### 2.2 接入步骤

1. `npm install next-intl`（注意 engines 要求 node >= 24.14.1）
2. 新建 `i18n/routing.ts`、`i18n/request.ts`
3. 在 `next.config.ts` 中用 `withNextIntl('./i18n/request.ts')` 包裹原配置（加 `[CN-FORK]` 注释标记，便于冲突识别）
4. 在根 layout 挂 `<NextIntlClientProvider>`
5. `middleware.ts` 处理 locale 检测：优先读用户 cookie / localStorage，其次 `Accept-Language`，默认 `zh-CN`
6. 提供语言切换入口：建议放在左侧导航底部（`src/components/leftnav.tsx` 或 `src/components/shared/Sidebar.tsx`）

### 2.3 组件改造范式

```tsx
// 改造前
<h1>Virtual Keys</h1>
<Button>Create New Key</Button>

// 改造后
const t = useTranslations('keys');
<h1>{t('title')}</h1>
<Button>{t('createNew')}</Button>
```

对应 `messages/zh-CN.json`：

```json
{
  "keys": {
    "title": "虚拟密钥",
    "createNew": "新建密钥"
  }
}
```

原则：**只替换用户可见字符串**，不碰变量名、props 名、CSS 类名、test id。

## 4. 字符串抽取工作流

1. 用脚本扫描目标目录，提取 JSX 文本节点与 `placeholder`/`title`/`aria-label`/`toast.*()` 等可见文案（可先用简单 AST 脚本生成初稿，避免手工全量排查）
2. 生成 `messages/en.json`（key 命名：`<页面>.<语义>`，如 `keys.table.header.name`）
3. 人工翻译为 `messages/zh-CN.json`
4. 替换组件中的硬编码字符串为 `t()` 调用
5. 跑该目录的既有测试；测试中若断言了英文字面量（如 `getByText("Create New Key")`），同步更新为断言译文或使用 i18n 感知的查询（**禁止**为了测试通过而保留英文硬编码）

## 5. 风险与缓解（重点）

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 与上游冲突 | **高** | 汉化必须触碰大量上游组件文件，上游每周都在改 UI | ① 只改字符串不改结构；② 单批次改动集中在少数目录；③ 每月同步后优先修冲突，冲突集中在 `t()` 替换行的可直接取上游版本再重放译文；④ 译文集中在 json，即使代码冲突也不会丢翻译 |
| 翻译遗漏导致中英混杂 | 中 | 全量覆盖不现实 | next-intl 未命中 key 自动回退英文（不空白、不报错）；按批次逐页验收 |
| 引入 i18n 破坏现有交互 | 中 | 涉及 Provider 注入与 layout 改动 | 先只做第 1 批试点，验证构建、测试、SSR 行为后再铺开 |
| 字符串拼接破坏语序 | 中 | 英文拼接式文案直译成中文会语序错乱 | 使用 next-intl 的 ICU 占位符（`{count}`、`{name}`）而非字符串拼接 |
| 测试断言英文字面量 | 低 | 大量 component test 断言英文文案 | 改动页面的测试同步更新（见 4.5），纳入批次完成定义 |

## 6. 验收标准

- [ ] 语言切换可用，偏好持久化（刷新后保持）
- [ ] 第 1-3 批页面在 zh-CN 下无可见英文残留（技术名词如 "API"、"Token" 例外，属保留项）
- [ ] 未汉化 key 回退英文，页面不报错、不空白
- [ ] `npm run build` 通过；`npm run test:component`、`test:integration` 全绿
- [ ] 上游同步演练后，汉化改动未丢失（译文函数仍生效）
