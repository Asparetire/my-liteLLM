## 1. 背景与目标

LiteLLM 上游（BerriAI/litellm）每日合入数十个 PR，任何二开改动都会成为未来的合并冲突源。本需求的目标是建立一套**让自有改动与上游演进长期共存**的仓库结构和工作流，使同步上游的成本保持在可预期水平。

## 3. 分支模型（铁律）✅

| 分支 | 用途 | 规则 | 状态 |
|---|---|---|---|
| `main` | 上游镜像 | **永不携带自有改动**；只允许 `merge --ff-only upstream/main` | ✅ 已建立 |
| `develop` | 自有改动集成基线 | 所有 feature 分支从它切出，完成后合回 | ✅ 已建立 |
| `feat/i18n-<批次>` | UI 汉化功能分支 | 按 02 号文档的批次切分 | ✅ 存在：i18n-ui-frontend |

| `feat/infra-<主题>` | 工程类改动 | 对应 08/09/10 号文档 | ✅ 存在：error-i18n-backend、doc-i18n-users |

### 3.1 同步上游的标准流程（建议每月一次，固定日期执行）✅

```bash
# Step 1: 同步 main（上游镜像）
git checkout main
git fetch upstream
git merge --ff-only upstream/main   # main 上永远应成功
git push origin main

# Step 2: 合并到 develop（自有改动基线）
git checkout develop
git merge main                      # 冲突只允许出现在这一步
# 解决冲突 -> 跑回归（见 10 号文档）-> git push origin develop
```

**演练记录：** 上次同步于 2026-09-17 执行，fetch upstream 获取约 200+ 个 upstream 分支。

### 3.2 降低冲突的工程手段 ✅

**改动隔离原则（按优先级）：**

1. 自有代码放全新目录（`litellm_cn/`、`docs/zh-CN/`、UI 的 `messages/`、`i18n/`）——零冲突
2. 无法隔离时，改动集中且加统一标记：

```python
# === [CN-FORK] BEGIN: token 配额分支 ===
if user_api_key_dict.max_token_budget is not None:
    ...
# === [CN-FORK] END ===
```

3. UI 汉化必然大面积触碰组件文件——这是**已知的最大冲突源**，缓解手段见 02 号文档第 5 节

**git 层辅助：**

- `.gitattributes` 对 `model_prices_and_context_window.json` 等频繁变动的生成文件标记 merge 策略，减少无意义冲突
- 同步演练记录冲突文件清单，若某文件连续 3 次冲突，评估重做隔离方案

## 4. 本机环境注意事项 ✅

## A. 附录：Git 操作速查

```bash
# 查看当前分支状态
git status
git branch -v

# 切换分支
git checkout <branch-name>

# 创建并切出新分支
git checkout -b feat/<new-feature>

# 查看远程仓库（upstream 只读 + backup 读写）
git remote -v

# 拉取上游代码
git fetch upstream

# 合并主分支到当前分支
git merge upstream/main

# 解决冲突后提交
git add <resolved-file>
git commit -m "Merge branch 'upstream/main'"

# 推送到远程
git push origin <branch-name>
```
